# APIs implemented by the current backend

## Appointments

- `GET /api/appointments`
- `GET /api/appointments/{id}`
- `GET /api/appointments/by-doctor/{doctorId}`
- `GET /api/appointments/by-patient/{patientId}`
- `GET /api/appointments/by-schedule/{scheduleId}`
- `GET /api/appointments/by-date?date=YYYY-MM-DD`
- `POST /api/appointments`
- `PUT /api/appointments/{id}`
- `DELETE /api/appointments/{id}`

Creating an appointment requires an active patient and schedule. The doctor,
date, and appointment time must match that schedule; duplicate patient bookings
and bookings over the schedule capacity are rejected.

## Reception

- `GET /api/receptions`
- `GET /api/receptions/{id}`
- `GET /api/receptions/by-date?date=YYYY-MM-DD`
- `GET /api/receptions/queue/room/{roomId}?date=YYYY-MM-DD`
- `GET /api/receptions/queue/doctor/{doctorId}?date=YYYY-MM-DD`
- `POST /api/receptions`
- `PUT /api/receptions/{id}`
- `PATCH /api/receptions/{id}/status`
- `DELETE /api/receptions/{id}`

Reception creates a patient record for a walk-in patient when the supplied
patient ID does not exist. A missing patient ID is generated by the backend.
The reception requires employee, room, and doctor IDs.

## Patient and doctor schedules

- `GET /api/patients/next-id`
- `GET /api/doctor-schedules/doctor/{doctorId}/date?date=YYYY-MM-DD`

Existing databases must apply
`docs/database/migrations/20261002_add_walk_in_patient_fields.sql` before
starting the updated backend.
